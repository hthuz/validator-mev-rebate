# 专利选题重定位（修订版）：只留有确定答案的技术特征

> 本版相对上一版的唯一改动：**删掉所有"评估类"特征**——评分、权重、阈值、置信度、健康度、优先级、等级。
> 理由：这些词的取值没有唯一解，审查员一定会问"凭什么定成 0.35 而不是 0.4"，答复时只能说是"经验值"，等于自认主观；重则被归入"人为设定的规则"，落入智力活动规则条款。
> 保留的判断标准只有一条：**同一份输入，任何人复算都必须得到同一个输出，且输出只能是布尔值、整数或地址/哈希集合。**

---

## 1. 判定一条特征是否"客观"的三条检验

| 检验 | 通过 | 不通过 |
|---|---|---|
| 可复算 | 给定输入，复算得同一结果 | 依赖经验系数、调参 |
| 无量纲参数 | 只有 0/1、整数比较、地址相等 | 引入 0.35、1.25、0.75 这类系数 |
| 输出可核对 | 布尔、整数、索引、哈希集合 | 分数、等级、"健康/亚健康" |

三条全过的特征，才写进权 1。过不了的，只能放说明书当"可选优化"，不能进权利要求。

## 2. 替换表（把上一版的表述逐条换掉）

| 上一版写法 | 为什么不行 | 换成 |
|---|---|---|
| 证据向量**加权求和**，和值**超过阈值**判定同一实体 | 权重与阈值都是人为设定 | 收款地址**相等**、付款地址**相等**（地址比较，二值） |

## 3. P1（首推）一种跨签名者地址的三明治交易识别方法、装置及终端设备

### 3.1 要解决的具体问题

攻击方用不同地址分别发前置与后置，所以"同一 `from` 前后夹击"的判据召回为零。实测 100 个真实区块（25,768,193–25,768,292，33,303 笔，14,893 个发送方）：**同地址三元组 0 例**。

### 3.2 六条判据（全部二值，无权重、无阈值）

从交易 calldata 直接解出 `(tokenIn, tokenOut, amountIn, amountOutMin, recipient)`，然后：

| 判据 | 内容 | 类型 |
|---|---|---|
| **C1** 同一接收合约 | 前置、受害、后置三笔的 `to` 地址**相等** | 地址相等 |
| **C2** 同对同向 | 前置与受害的 `(tokenIn, tokenOut)` **完全相等** | 地址对相等 |
| **C3** 方向逆序 | 后置的 `tokenIn` = 前置的 `tokenOut`，且后置的 `tokenOut` = 前置的 `tokenIn` | 地址相等 |
| **C4** 资金闭环 | 前置的 `recipient` **等于** 后置的 `from`（或等于后置的 `recipient`） | 地址相等 |
| **C5** 数量闭环 | `后置.amountIn ≤ 前置.amountOutMin` **且** `后置.amountOutMin ≥ 前置.amountIn` | 整数不等式 |
| **C6** 顺序 | `tx_index(前置) < tx_index(受害) < tx_index(后置)` | 整数比较 |

六条全部成立 → 输出该三元组与实体地址；任一不成立 → 不输出。**没有分数、没有置信度、没有"疑似"。**

两个设计要点，都要写进说明书：

- **C4 是"跨签名者"的技术核心**。前置把换得的代币发给收款地址 R，后置又从 R 支出同一代币——`R == 后置.from` 是**地址相等**，不是"行为相似"。这一条把"不同签名者"客观地连成一个资金闭环，不需要任何相似度打分。
- **C5 用成交下限代替实际成交量**：数据里没有 receipt，拿不到真实 `amountOut`，只有 `amountOutMin`。用下限做不等式只会**漏报、不会误报**，这是可辩护的保守判据（且"保守"是数学性质，不是主观选择）。

### 3.3 权 1 骨架

> 一种跨签名者地址的三明治交易识别方法，其特征在于，包括：
> 解析目标区块内各交易的调用数据，得到输入代币地址、输出代币地址、输入数量、最小输出数量与收款地址；
> 选取去向地址相同、且交易索引严格递增的第一交易、第二交易与第三交易，其中第一交易与第二交易的输入代币地址与输出代币地址分别相同；
> 判断第三交易的输入代币地址等于第一交易的输出代币地址、且第三交易的输出代币地址等于第一交易的输入代币地址；
> 判断第一交易的收款地址等于第三交易的签名者地址；
> 判断第三交易的输入数量不大于第一交易的最小输出数量，且第三交易的最小输出数量不小于第一交易的输入数量；
> 上述判断全部成立时，输出由所述第一交易、第二交易、第三交易构成的交易三元组及其签名者地址。

关键：权 1 里**只有"判断……等于 / 不大于……"**，没有一个"计算得分"。这是这份稿子能不能过的分水岭。

### 3.4 实测（判据可算性，不是命中率）

在 100 区块上按 V2 路由（`0x7a250d56…`）做了 ABI 解码验证：

| 项 | 数值 |
|---|---|
| V2 路由交易 | 101 笔 |
| 成功解出 path / amountIn / amountOutMin / recipient | **99 笔（98%）** |
| 该子集内相邻三元组 | 12 个 |
| 满足 C1–C6 | 0 个 |
| V2 路由占全部 swap 类交易 | 90 / 772 = **11.7%** |
| 聚合器入口（`0x3593564c` / `0x765e827f`）占比 | 535 / 772 = **69.3%** |

结论有两层，都该写进说明书：
1. **判据可算**——99/101 能完整解出四个字段，工程上成立；
2. **覆盖面是硬约束**——69.3% 的 swap 走聚合器命令流，只解 V2 接口召回必然不足。所以权 1 前序写"解析调用数据得到……"，把聚合器命令流的解析放从属权项，而不是假装全都能解。

这比"加权打分得出 38 例疑似"诚实得多，也更难被驳。

## 4. P2 一种订单流插入位置与被挤出交易集合的确定方法、装置及终端设备

**改名理由**：原叫"危害评估"，"危害"是评价；实际输出全是整数和集合，叫"确定"才名实相符。

**输出（三个，全是客观量）**
- `insertionIndex`：整数，插入位置
- `displacedTxs`：哈希集合，被挤出区块的交易
- `gasUsed`：整数，占用区块空间

**计算步骤（`internal/sim/replay_sim.go` 已实现，无一处主观参数）**
1. 排序单价 = Σ(优先费 × 燃料) / Σ燃料 —— 整数除法，确定值（L88-93）；
2. 在历史交易序列中取第一个"优先费单价小于该单价"的位置 —— 确定规则（`resolveInsertionIndex` L298-305）；
3. 剔除与订单流 `(from, nonce)` 冲突的历史交易 —— 相等判断（`conflictsWithBundleNonce` L289）；
4. 自尾部逐笔剔除至总燃料 ≤ 区块上限 —— 整数累减（L102-108）。

**权 1 骨架**

> 一种订单流插入位置确定方法，其特征在于，包括：将订单流中各交易的优先费与燃料消耗之积求和后，除以燃料消耗之和，得到整数排序单价；在目标区块的历史交易序列中，按顺序查找首个优先费单价小于所述排序单价的历史交易，以其索引作为插入位置；剔除与所述订单流发送方地址相同且序号相同的历史交易，并计入被挤出集合；将订单流插入后按燃料自序列尾部逐笔剔除交易直至燃料总和不大于区块上限，将剔除的交易哈希计入所述被挤出集合。

**已知偏差（必须披露）**：`estimateBundleGasUsed`（L338-351）只算 intrinsic gas，不含执行开销，会低估被挤出笔数。实施例要么注明"按 intrinsic 估算"，要么补一张固定系数的折算表（系数一旦固定就是确定值，不算主观）。

## 5. P3 / P4 / P5 的处理

**P3（签名派生 matchingHash 引用）——本来就客观，直接可用。**
签发（对 bundleHash 签名后取哈希）、索引（matchingHash → bundleHash）、校验（被引用方须声明 `HintHash`，布尔）、解析（替换、区间取交集、重算哈希）。全流程没有一个浮点数。四件里唯一"零改造"就能交的。

**P4（提示字段确定性截断）——保留，但改词。**
"隐私等级""保护强度"这类表述删掉，改成可核对的规则：字段子集（位掩码）+ 十进制保留位数（gasPrice 3 位、gasUsed 2 位，其余位清零）+ 事件签名白名单（只留 topic0，Balancer 加保留 poolId）。"确定性"本身就是区别特征——与差分隐私的随机噪声相比，同一交易对任何订阅方输出**逐字节相同**，可审计复现。
前提：先修 `buildReplayBodyLogs`（L324-336）只填 Address 不填 Topics 的问题，否则 SpecialLogs 恒空，实施例跑不出东西。

**P5（返还拆分）——建议暂缓。**
想得出的"公平"规则都带主观性（边际贡献、加权比例）。客观版本只剩两类：按 `gasUsed` 整数占比，或直接执行已声明的 `percent`（那就只是照抄输入，无技术贡献）。等有确定规则再立项。

## 6. 顺带一个提醒：现有那件专利的风险点

现有专利本体就是评分机制（`registry.go:246-315`：五个因子相乘、1%/5% 非对称平滑、0.35/0.12/0.20 等系数）。这些系数是它最容易被质疑的地方——答复审查意见时很难解释"为什么是 0.20 不是 0.25"。

若那件还要推进，最小改动的补救是把**处置动作**从"评分降到阈值"改成"计数达到 N 即拒绝分发"：

- 原：`sandwichFactor = clamp(1 − 0.20 × 次数, 0.10, 1.0)` → 分数下降
- 改：同一实体在滑动窗口内命中 P1 判据 **N 次**（N 为整数，如 3），即拒绝向其分发

计数是客观的，N 是策略参数而非"权重"，答辩时可以说"这是运营阈值，不是技术判断依据"。这样一改，现有专利自然引到 P1 上，两件形成"识别 → 处置"的引用关系，而不是互相覆盖。
