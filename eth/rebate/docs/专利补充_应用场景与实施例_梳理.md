### 实施例 1：区块生产者动态评分的单次观测计算

**技术细节**

画像模块维护每个 builder 一条 `BuilderStats` 记录，包含：分发尝试次数、成功次数、失败次数、连续失败次数、sandwich 次数、well-behaved 次数、有价值订单流次数、reward 样本数/累计/平均/最近值。一次观测 `Observe()` 合并后重算动态评分：

```
target_score = base_score
             × reliability_factor     // 可靠性
             × failure_factor         // 连续失败惩罚
             × sandwich_factor        // 异常行为惩罚
             × well_behaved_factor    // 正向行为奖励
             × value_factor           // 价值产出奖励

target_score = clamp(target_score, 0.5, 100)      // 百分制上下限
target_score = min(target_score, base_score + 15) // 相对基础分上限 +15
target_score = target_score × competition_factor  // 竞争集中度惩罚（见实施例6）

score_{t+1} = score_t + (target_score − score_t) × rate
rate = 0.01（目标高于当前） / 0.05（目标低于当前）  // 非对称平滑
```

各因子取值（可直接写入实施例的数值实例）：

| 因子 | 定义 | 区间 |
|---|---|---|
| reliability_factor | `clamp(0.5 + 成功率, 0.35, 1.50)` | 0.35–1.50 |
| failure_factor | `clamp(1 − 0.12 × 连续失败次数, 0.40, 1.0)` | 0.40–1.0 |
| sandwich_factor | `clamp(1 − 0.20 × sandwich次数, 0.10, 1.0)` | 0.10–1.0 |
| well_behaved_factor | `clamp(1 + 0.05 × 正向行为次数, 1.0, 1.5)` | 1.0–1.5 |
| value_factor | `1 + clamp(log10(1 + 产出ETH) × 0.20, 0, 0.75)` | 1.0–1.75 |

**如何操作**

1. 启动时按配置注册 builder 并给 `base_score`（配置项 `dispatcher.builders[].score`，取值必须落在 (0,100]）。
2. 每次分发后系统自动调用 `Observe(builder, {DispatchAttempts:1, DispatchSuccesses:0/1, ValueCreatedWei})`；
   也可通过运行接口手工注入：`POST /builders/observe`。
3. 通过 `GET /builders/scores` 读取 `baseScore / score / stats / explorationCandidate`。

**预期效果**

- 单次观测只按目标差值的 1% 移动，因此不会一次成功就跳分；
- 目标分上限为 `base + 15`、全局上限 100，正常生产者**不会无限增长**；
- 负向步长（5%）> 正向步长（1%），异常行为下降快于正常上升，对应**权 4**。

### 实施例 2：Reward 学习与近期收益质量信号

**技术细节**

reward 作为近期收益质量的即时信号，与长期评分解耦：

```
reward = 1.00 × 成功率
       + 0.60 × value_component        // clamp(log10(1+产出ETH) × 0.20, 0, 0.75)
       + 0.15 × wellBehaved_component  // clamp(正向次数 × 0.05, 0, 0.50)
       − 0.70 × 失败率
       − 1.10 × sandwich次数
reward = clamp(reward, −2.0, 2.0)
```

每次观测累加：`RewardSamples++`，`AverageReward = TotalReward / RewardSamples`。若外部直接给出 reward，则取 `clamp(给定值, −2, 2)`。

**如何操作**

- 正常分发链路自动计算；外部注入时 `POST /builders/observe` 可传 `reward` 字段覆盖自动计算。
- 读取 `stats.rewardSamples / averageReward / lastReward`。

**预期效果**

- reward 反映**短期状态变化**，average_reward 越接近 +2 表示近期表现显著优于长期；越接近 −2 表示近期恶化。
- 与动态评分联合后（实施例3），既能对近期恶化快速响应，又不会被单次波动带偏。

### 实施例 3：expected_reward 联合指标

**技术细节**

长期信誉（动态评分）与近期质量（average_reward）相乘，得到统一优先级：

```
expected_reward = max(score, 0.5) × max(1 + clamp(average_reward, −2, 2), 0.10)
```

- 加分项：`average_reward > 0` 时提升，> 0 越多倍率越大（上限 3.0）；
- 惩罚项：`average_reward < 0` 时按比例衰减，最低保留 0.10 倍，防止归零后彻底失去机会。

**如何操作**

- 无独立接口，作为 `DispatchDecision.ExpectedReward` 随分发出现在日志（`builder_dispatch_selected`）与 JSONL 的 `expected_reward` 字段。
- 也可作为健康度/优先级指标由结果输出模块对外提供。

**预期效果**

- 避免"只看长期均值→对恶化响应慢"和"只看短期 reward→评估震荡"两种退化，对应**权 6**。

### 实施例 4：探索候选识别与 UCB 探索分值

**技术细节**

满足以下任一条件即纳入探索候选集合：

1. `分发尝试次数 < min_explore_dispatches`（默认 5）；
2. `当前时间 − 注册时间 < new_producer_grace_period`（默认 600s）。

探索分值为"预期收益 + 样本不足补偿 + 新生奖励 + 不确定性权重"，再叠加 UCB bonus：

```
exploration_weight = max(expected_reward, 0.5)
                   × (1 + uncertainty_weight × missing/min_explore_dispatches)   // 样本不足补偿
                   × (1 + fresh_producer_bonus × freshness)                      // 新生奖励
                   × (1 + uncertainty_weight / sqrt(attempts + 1))               // 不确定性权重

bandit_score = exploration_weight
             + uncertainty_weight × sqrt( ln(总拉取数 + 1) / (rewardSamples + 1) ) // UCB bonus
```

在探索候选集合内按 `bandit_score` 加权随机选择，对应**权 7、权 8**。

**如何操作**

- 配置 `dispatcher.strategy`：`min_explore_dispatches`、`new_producer_grace_period`、`uncertainty_weight`、`fresh_producer_bonus`。
- 分发表现为 `layer = exploration`，`reason = ucb_reward_plus_uncertainty`。

**预期效果**

- 样本越少、注册越新，探索分值越高，新生产者必得冷启动流量；
- 样本增多后 UCB bonus 自然衰减，平滑过渡到利用阶段。

### 实施例 5：探索 / 利用分层切换（alternating 与 probabilistic）

**技术细节**

系统按样本充分性把 builder 分成探索候选集与成熟集，命中探索条件时走探索评估，否则走利用评估。两种分层触发模式：

- `alternating`：维护 `nextExplore` 布尔量，每次存在探索候选时严格 1:1 交替，保证长期探索/利用各占 50%；
- `probabilistic`：以 `exploration_rate`（默认 0.20）随机进入探索层。

利用层按 `expected_reward` 加权随机选择目标 builder；探索层按 `bandit_score` 加权随机选择。对应**权 1**。

**如何操作**

```yaml
dispatcher:
  strategy:
    exploration_enabled: true
    exploration_mode: alternating      # 或 probabilistic
    exploration_rate: 0.20             # 仅 probabilistic 生效
    min_explore_dispatches: 5
    new_producer_grace_period: 600s
    uncertainty_weight: 1.25
    fresh_producer_bonus: 0.75
```

**预期效果**

- 交替模式下 exploration 与 exploitation 长期各占 50%（实验实测 12809 : 12809）；
- 相邻两次分发的分层**必然切换**，避免连续偏置。

### 实施例 6：竞争集中度惩罚（防流量集中 / 去中心化）

**技术细节**

在利用层对"份额过高"或"相对 reward 偏低"的 builder 施加惩罚：

```
expected_share = 1 / builderCount
actual_share   = 该builder分发次数 / 全部分发次数
concentration_penalty = (actual_share − expected_share) × 0.35   (仅当 actual_share > expected_share)
relative_reward_penalty = (1 − clamp(avg/max_avg, 0, 1)) × 0.10  (仅当 avg < max_avg)
competition_factor = 1 − clamp(concentration_penalty + relative_reward_penalty, 0, 0.15)
```

竞争因子直接乘进动态评分目标值，因此**份额越高、评分上限被压得越低**。对应**权 9**。

**如何操作**

- 无独立配置项，随 `recalculateScoresLocked()` 每次观测后自动生效。
- 观察 `GET /builders/scores` 的 `score` 与其分发占比是否收敛。

**预期效果**

- 单点最高分发占比被限制在合理区间（10000 区块实验中最高占比 alpha 为 23.6%，未形成独占）；
- 头部 producer 仍保持领先，但不会无上限增长。

### 实施例 7：恶意区块生产者的快速抑制（端到端）

**技术细节**

通过 `POST /builders/observe` 注入包含 `sandwichAttacks` 的观测，评分链路自动执行：
`sandwich_factor = clamp(1 − 0.20 × 累计sandwich次数, 0.10, 1.0)`，同时 `reward` 中扣 `1.10 × sandwich次数`，且负向平滑步长（0.05）为正向（0.01）的 5 倍。

**如何操作**

```bash
# 1) 注入恶意行为观测
curl -X POST localhost:8080/builders/observe -d '{
  "builder":"builder-epsilon",
  "dispatchAttempts":200,"dispatchSuccesses":160,
  "sandwichAttacks":10
}'
# 2) 查看评分与是否仍为探索候选
curl localhost:8080/builders/scores
```

**预期效果（真实实验数据）**

| Builder | 初始分 | 最终分 | 说明 |
|---|---|---|---|
| epsilon（持续 sandwich） | 13 | 1.70 | 分发占比仅 1.8% |
| theta（85 分起步，6000 区块后作恶） | 85 | 19.12 | 高分不豁免，同样快速降权 |

结论：惩罚**不依赖低初始信誉**，高分 producer 一旦持续作恶同样被快速降权，对应**权 4、权 5**。

### 实施例 8：新加入区块生产者的冷启动与端到端 mock 实验

**技术细节**

运行期间通过 `POST /builders/register` 动态注册新 builder（`score=60`），注册瞬间即满足"样本 0 < 5"和"处于 600s 宽限期"，被标记为 `explorationCandidate=true`，进入探索候选集合分得冷启动流量。

**如何操作**

```bash
curl -X POST localhost:8080/builders/register \
  -d '{"name":"builder-zeta","url":"http://localhost:18550","score":60}'
```

实验配置：5 个初始 builder（alpha 85 / beta 67 / gamma 50 / delta 27 / epsilon 13）→ 运行约 3000 区块后注册 zeta(60) → 继续到约 10000 区块，`exploration_mode: alternating`。

**预期效果（真实实验数据，共 25618 次分发）**

| Builder | 分发次数 | 占比 | 最终 score |
|---|---:|---:|---:|
| alpha | 6050 | 23.6% | 97.16 |
| beta | 5054 | 19.7% | 80.61 |
| gamma | 4170 | 16.3% | 64.55 |
| theta（后期作恶） | 3518 | 13.7% | 19.12 |
| zeta（中途加入） | 3824 | 14.9% | 74.78 |
| delta | 2542 | 9.9% | 39.63 |
| epsilon（恶意） | 460 | 1.8% | 1.70 |

- 探索 : 利用 = 12809 : 12809（严格 1:1）；
- 中途加入的 zeta 获 3824 次分发（其中 2000 次来自探索），分数升至 74.78；
- 头部占比 23.6%，未形成集中；恶意者被压制到 1.8%。
- 该实施例同时覆盖**权 1、权 7、权 9**，并可作为"有益效果"的定量支撑。

### 实施例 9（可选）：健康评估 / 准入控制 / 风险预警输出

**技术细节**

结果输出模块把内部状态映射为对外结论：

- **健康评估**：以 `score`、`averageReward`、成功率、sandwich 次数构成健康度；
- **准入控制**：注册时校验 `score ∈ (0,100]`、名称唯一，否则拒绝；运行中低于最低有效分（0.5）的 producer 可拒绝继续分发；
- **风险预警**：`sandwichAttacks` 或连续失败超阈值时输出预警。

**如何操作**

- 读取 `GET /builders/scores`（含 `explorationCandidate`）作为对外健康/风险视图；
- 准入拒绝示例：注册 `score=0` 或重名会被返回 400 并带原因。

**预期效果**

- 同一套评分输出可直接支撑排序、健康评估、准入建议、风险预警、调度五类结果，对应**权 1 末段与权 10**，体现"独立可复用的底层能力"这一有益效果。
