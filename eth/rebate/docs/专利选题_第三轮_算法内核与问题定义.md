# 专利选题（第三轮）：先定义问题，再选算法内核

> 这一轮不再罗列"代码里有什么"，而是先回答两个问题：**这东西解决什么技术问题**，**它用了什么具体手段**。
> 判断标准照旧：同一份输入，任何人复算得到同一个输出；输出只能是布尔、整数、索引、哈希集合。

## 0. 直接回答你的两个问题

### 0.1 "订单流插入位置与被挤出交易集合的确定方法" 解决了什么问题

一句话：**在没有执行环境、没有 receipt、没有 trace 的条件下，只用同一区块的既有交易序列，算出候选订单流该插在哪、会挤掉谁。**

它输出三个量：插入位（整数）、被挤出交易集合（哈希集合）、占用燃料（整数）。

它为什么有用——因为"返还多少"这个问题必须先有"贡献多大"这个量，而贡献 = 该订单流带来的优先费 − 因它被挤出的交易损失的优先费。后一项必须知道"挤掉了谁"，而"挤掉了谁"必须重排区块，重排需要执行环境。没有执行环境，就只能用既有序列做影子打包。

**所以它的真实定位是：给"贡献"提供一个可计算的量纲。** 它是中间件，不是最终产品。

**但它单独报，创造性撑不住。** 理由很具体：

| 步骤 | 现在的做法 | 为什么弱 |
|---|---|---|
| 插入位 | 线性扫描找第一个"优先费单价更低"的位置（`resolveInsertionIndex`，L298-305） | 一次 for 循环，任何工程师都会这么写 |
| 剔除 | 从尾部逐笔删到装得下（L102-108） | 更朴素，连分支都没有 |
| 排序单价 | Σ(优先费×gas)/Σgas（L88-93） | 一次整数除法 |

三步全是 O(n) 朴素扫描。审查员一句"常规技术手段"就能驳回。

**但只要场景从"一个订单流"变成"多个订单流争用同一个区块"，朴素扫描立刻失效**——因为每加一个订单流就要重扫一遍，且结果跟处理顺序绑定。那才是真问题。这就引出方案 A 和方案 B。

### 0.2 "bundle 利益分配" 解决了什么问题

现有代码的做法是：`refundable = 优先费 × 10%`（`replay_sim.go:19` 定义常数，L154 使用），`dispatcher.go:481-493` 再把 `Profit + RefundableValue` 相加当成"创造的价值"。

三个能说清楚的客观缺陷：

1. **与贡献无关**。常数比例。挤掉 20 笔交易的订单流，和一笔没挤掉的，拿同一个比例。
2. **不守恒**。m 个订单流各按 10% 累加，无人保证 Σ ≤ 该区块实际新增收益。极端情况下返还总额可以超过区块新增的优先费。
3. **不可复算**。返还额依赖模拟时的中间状态（`stateBlock`、队列顺序），第三方拿不到同样的输入就算不出同样的数。

**"分配"这个词要小心。** 权利要求里写"分配"，容易被归入商业规则/智力活动规则（专利法第 25 条）。同样的技术内容，落点写成"**数额的确定** + **一个可检验的恒等式**"，就是数据处理方法。

所以准确的问题定义是：

> 如何在多个订单流互相挤占（后插入的会把先插入的挤出）的条件下，确定每个订单流的收益额整数，使得这些整数之和**恒等于**整块新增收益，且不含任何比例参数。

这个定义一旦写死，"公平"就不再是问题——不讨论怎么分才对，只讨论"和必须等于被分的那个总量"。这是数学约束，不是价值判断。

## 1. 方案 A｜多订单流争用：带权区间调度

### 1.1 处理对象

- 目标区块既有交易序列 H（n 笔，每笔带燃料消耗 g、优先费 p）
- 候选订单流集合 {B₁…B_m}，每个带插入位 p_i、燃料需求 G_i、优先费总额 F_i
- 区块燃料上限 L

### 1.2 现有技术的缺陷（可验证）

`queue.Pop`（`queue.go:100-107`）线性扫描取第一个 `TargetBlock <= currentBlock+1` 的项，即**先进先出**；高优先级项被 `append([]*BundleQueueItem{item}, ...)` 插到队首（L54）。于是：

- 结果依赖到达顺序 —— 同一组订单流换一个到达顺序，被采用的集合不同，**不可复算**；
- 先到的低价值订单流占住燃料，后来者被挤掉，**总优先费不是最大**；
- 每个订单流重扫一遍历史序列，**O(m·n)**。

### 1.3 技术手段

1. **把燃料轴拉直。** 对 H 做燃料前缀和 `S[j] = Σ_{i≤j} g_i`，则"在第 p 位插入"变成燃料轴上的坐标 `S[p]`。每个订单流映射为一个左闭右开区间 `I_i = [S[p_i], S[p_i] + G_i)`。
2. **冲突判据 = 区间相交**（整数比较 `I_i.left < I_j.right && I_j.left < I_i.right`），或两者的 `(from, nonce 区间)` 相交。
3. **原子性合并。** 同一签名者的多个订单流共享 nonce 域，必须同时入选。把它们合并成一个**超区间**：左端取 min、右端取 max、权值取 ΣF_i。这一步是区间图上的"团收缩"，是方案 A 里唯一不那么显然的动作。
4. **在超区间集合上求最大权独立集。** 按右端点升序排，`dp[k] = max(dp[k-1], w_k + dp[pred(k)])`，`pred(k)` 用二分查找（右端点 ≤ 第 k 个左端点的最后一个）。区间图的最大权独立集是多项式可解的，这一步是精确最优，不是贪心。
5. 回溯 `dp` 得到被选集合，再展开超区间为订单流索引。

### 1.4 输出

- 被选订单流索引集合（整数集合）
- 总优先费（整数 wei）
- 每个被选订单流的最终插入位（整数序列）

### 1.5 技术效果

| 项 | 现有 | 本方案 |
|---|---|---|
| 结果与提交顺序 | 相关 | **无关**（输入集合相同 → 输出逐位相同） |
| 总优先费 | 贪心，非最优 | **区间图上最优**，可给最优性证明 |
| 复杂度 | O(m·n) | O(n + m log m) |

最优性证明本身就是说明书的加分项：把"区块空间分配"显式建模为区间图，从而把贪心问题转成 DP 问题——这个建模步骤是创造性所在。

## 2. 方案 B｜收益额确定：保序前缀增量（首推）

### 2.1 处理对象

- 一个区块的交易序列（每笔带 g、p）
- 该区块中被转发的订单流，**按插入位升序编号 1…m**

### 2.2 要解决的技术问题

见 §0.2：确定整数 d₁…d_m，满足 Σd_k = 整块新增收益，且 d_k 反映第 k 个订单流的实际插入效果。

### 2.3 技术手段

**第一步：定义保序前缀状态。**
令 S_k = {B₁…B_k}，`v(S_k)` = 把前 k 个订单流按插入位依次插入、再从尾部逐笔剔除至总燃料 ≤ L 之后，区块内全部交易的优先费之和（整数）。

**第二步：增量取差。**
`d_k = v(S_k) − v(S_{k−1})`，整数，**可以为负**。

**第三步：望远镜求和。**
`Σ_{k=1..m} d_k = v(S_m) − v(S_0)`。

这是恒等式，不是近似。它的意义：守恒不需要任何归一化、不需要最大余数法、不需要四舍五入。**没有参数，所以没有被质疑"凭什么这么定"的空间。**

**第四步：用一棵树把 m 次重放压成一次遍历。**

朴素做法是对每个 k 重排一遍，O(m·n)。改成：

- 维护一棵**按序隐式平衡树**（implicit treap），中序即区块内交易顺序，节点存 `(g, p)`，子树存 `Σg` 与 `Σp`；
- 插入订单流 = 在位置 p 处分裂、拼接，O(log(n+Σlen))；
- 求 `v(S_k)` = 从根下降找"最后一个使前缀 Σg ≤ L 的节点"，返回其前缀 Σp，O(log n)；
- 被剔除的后缀（哈希序列）就是下降路径右侧的子树，直接取中序遍历，O(k) 输出。

**第五步（顺带）：受害者损失。**
被剔除后缀的 `Σ(p×g)` 可从同一棵树的子树和直接读出，O(1)。这就是"被挤出交易损失了多少优先费"的客观值，可以对受害者返还——比只给 searcher 返还更完整。

### 2.4 输出

- 整数向量 (d₁…d_m)
- 每个订单流导致的被挤出交易哈希集合
- 恒等式 `Σd_k = v(S_m) − v(S_0)` 是否成立（布尔）

### 2.5 为什么这不是"智力活动规则"

权 1 的每一步都是：维护一个序列 → 查一次前缀和 → 做一次整数减法 → 输出一个整数。不涉及任何计价模型、费率、权重、阈值。第三方拿同一区块数据和同一订单流集合，复算出的 d 向量**逐位相同**，恒等式用一次加法就能核对。

### 2.6 与 Shapley 的取舍（写进说明书当创造性论证）

Shapley 值也满足 Σφ = v(N) − v(∅)，是"分配"的标准答案。但它要评估 2^m 个子集——m=20 时是 100 万次，m=100 时不可算。

本方案用**固定顺序的前缀增量**替换全部子集：只需 m 次，因为顺序由协议给出的整数（插入位）唯一确定，不是人为挑选。代价是结果依赖顺序，收益是复杂度从 2^m 降到 m。这个"用顺序换可计算性"的取舍是明确的技术选择，可以写进说明书作为创造性依据。

（术语上这等价于沿固定路径的离散 Aumann–Shapley 值。不用写进权利要求，但代理人可以用来说明"为什么不选 Shapley"。）

## 3. 实施例（数字能跑通，说明书可直接用）

设区块燃料上限 L = 400,000。既有交易：

| 交易 | gas | 优先费(gwei) | p×g |
|---|---|---|---|
| H1 | 21,000 | 2 | 42,000 |
| H2 | 150,000 | 3 | 450,000 |
| H3 | 200,000 | 1 | 200,000 |
| H4 | 100,000 | 5 | 500,000 |

**S₀（无订单流）**：累计 21k / 171k / 371k / 471k > L → 剔除 H4。`v(S₀) = 42,000 + 450,000 + 200,000 = 692,000`。

**S₁（插入 B₁：位 1，gas 50,000，优先费 600,000）**：序列 H1,B1,H2,H3,H4 → 累计 21k/71k/221k/421k/521k → 剔除 H4，仍 421k > L，剔除 H3 → 221k。`v(S₁) = 42,000 + 600,000 + 450,000 = 1,092,000`。
`d₁ = 1,092,000 − 692,000 = 400,000`。

> 注意：B₁ 自身贡献 600,000，但把 H3（200,000）挤了出去，净增量 400,000。固定 10% 会给出 60,000——两个数都不等于 400,000。

**S₂（插入 B₂：位 3，gas 30,000，优先费 150,000）**：序列 H1,B1,H2,B2,H3,H4 → 累计 21k/71k/221k/251k/451k/551k → 剔除 H4（451k），再剔除 H3（251k）。`v(S₂) = 42,000 + 600,000 + 450,000 + 150,000 = 1,242,000`。
`d₂ = 1,242,000 − 1,092,000 = 150,000`。

**核对**：`d₁ + d₂ = 550,000`，`v(S₂) − v(S₀) = 1,242,000 − 692,000 = 550,000`。✓

同一组数据，现有固定比例给 (60,000, 15,000)，本方法给 (400,000, 150,000)。差别不在大小，在于后者满足恒等式、且能解释为什么 B₁ 拿的比它自己的优先费少（被 H3 分走）。

## 5. 权 1 骨架

### 5.1 方案 B（首推）

> 一种区块内订单流收益额的确定方法，其特征在于，包括：
> 获取目标区块的交易序列，所述交易序列中每笔交易具有燃料消耗量与优先费；
> 获取待插入所述交易序列的多个订单流，每个订单流具有插入位置、燃料消耗量与优先费之和，并按插入位置升序编号；
> 对第 k 个订单流，以插入前的交易序列为第一状态，以插入后的交易序列为第二状态，在所述第二状态中自序列末端起逐笔剔除交易，直至剩余交易的燃料消耗量之和不大于区块燃料上限，得到第三状态；
> 分别计算所述第一状态与所述第三状态中全部交易的优先费之和，将二者之差作为第 k 个订单流的收益额；
> 令 k 自 1 递增至订单流数量，重复上述步骤，输出由各订单流收益额构成的整数序列；
> 其中，所述整数序列中各元素之和，等于第 m 个订单流插入后的优先费总和与插入前的优先费总和之差。

最后一句是区别特征，也是可当场验算的恒等式。

从属权项方向：
- 用按序平衡树维护序列、以子树燃料和做下降查找，一次遍历求出全部 v(S_k)；
- 剔除后缀的 `Σ(优先费×燃料)` 作为被挤出交易的损失额输出；
- 同一签名者的多个订单流视为一个整体参与编号。

### 5.2 方案 A

> 一种区块内多个订单流的选取方法，其特征在于，包括：
> 以目标区块既有交易序列的燃料消耗量前缀和，将每个订单流的插入位置与燃料消耗量映射为燃料轴上的一个区间；
> 将签名者地址相同且序号区间重叠的订单流合并为一个超区间，所述超区间的左端点为各区间左端点的最小值，右端点为各区间右端点的最大值，权值为各订单流优先费之和；
> 将全部超区间按右端点升序排列；对第 k 个超区间，二分查找右端点不大于其左端点的最后一个超区间，记其序号为前驱序号；
> 取第一值与第二值中的较大者作为第 k 个超区间对应的选取权值，所述第一值为第 k−1 个超区间对应的选取权值，所述第二值为第 k 个超区间的权值与前驱序号对应的选取权值之和；
> 回溯得到超区间集合，展开为订单流索引集合输出。

## 6. 复杂度与可验证性汇总（说明书的技术效果章节素材）

| 方案 | 处理对象 | 算法内核 | 输出 | 复杂度 | 可验证方式 |
|---|---|---|---|---|---|
| A | 订单流集合 × 区块燃料轴 | 区间图最大权独立集（DP + 二分） | 索引集合 + 整数总费 | O(n + m log m) | 换顺序复算，输出不变 |
| B | 区块交易序列 × 订单流序列 | 保序前缀增量 + 隐式平衡树 | 整数向量 + 哈希集合 | O((n+Σlen) log n) | 求和的望远镜恒等式 |
| （原 P2） | 单个订单流 × 区块序列 | 三次线性扫描 | 索引 + 哈希集合 | O(n) | 无恒等式，无可验性 |

第三行就是 P2 单独报的问题：**没有可检验的性质**。方案 A 有"顺序无关"，方案 B 有"和的恒等式"，都是审查员和对手都能当场算的东西。这是这三行真正的差距。

## 7. 先后与风险

**报一件 → B。** 对象具体（一个区块内的订单流序列），问题具体（守恒 + 可复算），手段具体（保序前缀 + 平衡树下降），输出是整数向量加一个恒等式。不含任何比例、权重、阈值。

**报两件 → B + A。** 两者对象不重叠：B 是"给定已选集合后算钱"，A 是"从候选里选集合"。A 引用 B 的输出，形成"选取 → 计价"的链条，而不是互相覆盖。原来的 P2 降为 B 的实施例（§3 那组数字就是它）。

**风险点，必须提前处理：**

1. **`estimateBundleGasUsed` 只算 intrinsic gas**（L338-351），不含执行开销。实施例里的 gas 数字会偏小，被挤出笔数会被低估。要么在说明书里明确"按 intrinsic 估算"，要么加一张折算表。**不能装作没这回事**——对手拿真链数据一比就露。
2. **`v(S_k)` 用 `p × g` 作为收益代理**。这是协议定义的量（effectiveGasPrice − baseFee），客观；但要在说明书里说明"以优先费为收益口径"，否则会被问"为什么不算 MEV 利润"。
3. **顺序依赖要主动披露**。d 向量依赖插入位序。这不是缺陷——插入位是协议给出的整数，唯一确定——但必须写清楚"不同顺序得到不同向量，本方法以插入位序为准，故结果唯一"。主动说比被问出来好。
4. **A 的最优性只在线性约束下成立**。如果订单流之间存在跨区间的状态依赖（后置依赖前置的池子状态），区间图模型不成立。权 1 要把范围限定在"燃料轴区间 + 序号区间"这两类冲突，其余放说明书讨论。
